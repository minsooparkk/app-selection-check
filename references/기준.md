# Application 선정의 기준 (풀이)

## 대원칙
"Garbage in, Garbage out". Input 이 업무 품질의 8할을 차지한다. 최우선 목표는 Input 을 AI 가 잘 읽고 처리할 수 있게 정형화하는 것이다. 잘 "처리"하는 것보다 좋은 데이터를 모으는 시스템을 설계하는 것이 우선이며, LLM 이 발달할수록 "처리"의 중요성은 낮아진다.

- 오해 (X): Skill, Tool 의 어떤 기능이 좋고, 내 업무에 어떻게 적용하는가
- 올바른 접근 (O): 어떤 MCP 와 Database 로 Input 을 어떻게 잘 구축하는가

## Workflow 설계의 기본 원칙
1. Deterministic 하게 처리할 수 있으면 최대한 Deterministic 하게 처리한다. 메일을 읽으려면 API 나 MCP 를 지원하는 메일 앱을 쓴다. API 가 없는 웹메일을 고집하면서 화면 조작 브라우저로 읽으면 비효율적이고 품질의 일관성을 유지하기 어려우며 매일 유지보수해야 한다. 차라리 쓰지 않는 편이 낫다.
2. 비정형 데이터의 정형화는 LLM 이나 외부 서비스의 도움을 받는다. 단, 외부 서비스는 API 또는 MCP 를 쉽게 제공해야 한다. 녹음 전사 파일은 처음에 화자가 분리되어 있지 않으므로 LLM 으로 화자를 분리하고 정제한다.
3. 배보다 배꼽이 더 크면 안 된다. Input Channel 이 "잘" 연결되지 않으면 과감히 포기한다. 다듬는 데 너무 많은 리소스를 쓰지 않는다.

## 선정 기준과 이 스킬의 구분

| 기준 | 스킬의 구분 | Input 관리 방법 |
|---|---|---|
| 1. API·MCP 가 있는 앱. 반드시 이런 앱 위주로 쓴다 | 1 유지(API·MCP) | Deterministic 한 Script. 유지보수 리소스가 극도로 낮다 |
| 2. API·MCP 가 없지만 어쩔 수 없이 써야 하는 대규모 플랫폼(예: 국민 메신저) | 2 유지(대형 플랫폼) | 로컬 명령줄 도구, 또는 화면 조작 AI 로 하루 한 번 대화 내용 내보내기 → 정리 |
| 3. 통화·회의록처럼 파일로 남는 자료 | 3 유지(로컬 정형화) | 로컬 받아쓰기 + 폴더 동기화 + LLM 으로 전사와 정형화 |
| 어느 기준에도 들지 않고 바꿀 수 있음 | 교체 | API·MCP 가 있는 대안 앱으로 |
| 어느 기준에도 들지 않고 바꿀 수도 없음 | 포기 검토 | 연결하지 않는다(원칙 3) |

## 근거 칸과 판정 규칙 (scripts/judge.py 가 적용)
- `api.status=yes` 는 `api.url` 이 있어야 인정. `api.reads_my_data=yes` 여야 1번으로 본다.
- `mcp.status=yes` 는 `mcp.url` 이 있어야 인정. `mcp.official≠yes` 이고 API 도 없으면 '판단 필요'.
- `no` 는 `checked_on` 이 있어야 인정.
- API·MCP 가 없을 때: `local=yes` 이고 `major_platform=yes` → 2, `local=yes` → 3, `local=no` 이고 `major_platform=no` → 교체, `local=no` 이고 `major_platform=yes` → 포기 검토.
- 칸이 `unknown` 이면 미정 또는 불확실. 사용자가 정할 것이 남으면 판단 필요.
